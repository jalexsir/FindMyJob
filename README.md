# FindMyJob 🤖

FindMyJob — Telegram-бот для пошуку IT та Defence-tech вакансій, який я розробив і самостійно задеплоїв у продакшн. Бот агрегує вакансії з RSS-джерел DOU та Djinni одразу для 33 категорій, паралельно опитуючи до 20 ендпоінтів через ThreadPoolExecutor, і усуває дублікати на трьох рівнях — усередині фіду, між варіантами одного сайту та між різними сайтами. Реалізував власний парсер заголовків DOU з евристиками для розпізнавання компанії, зарплати та міста з неструктурованого тексту, включно з нормалізацією кириличних гомогліфів і валідацією хибних кандидатів. Для наочності вакансій генерую унікальні зображення-картки на льоту через Pillow. Персональні списки «Обране» та «Вилучені з пошуку» зберігаються persistently в SQLite (WAL-режим) окремо для кожного користувача та переживають перезапуски. Проєкт написаний на Python із бібліотекою python-telegram-bot і має шарову архітектуру — домен, сервіси (фіди, сховище, зображення) та Telegram-шар — з чіткою ін'єкцією залежностей, що робить код тестованим і легко розширюваним. Написав диференційні та інтеграційні тести, що звіряють поведінку системи проти попередніх версій при рефакторингу. Задеплоїв бота на Oracle Cloud (Always Free VPS) під керуванням systemd з автоматичним перезапуском при збоях. Налаштував CI/CD через GitHub Actions: кожен push у master автоматично розгортається на сервері через SSH-деплой з оновленням залежностей і рестартом сервісу без ручного втручання. Секрети (токен бота) винесені в .env і не потрапляють у репозиторій. Проєкт демонструє повний цикл розробки: від парсингу неструктурованих даних і проєктування архітектури до автоматизованого деплою й підтримки в продакшні.

## Функціонал

### Крок 1 — Вибір категорій (`/start`)

Бот показує інлайн-клавіатуру вибору категорій.

- **33 категорії**, по 2 в рядку, з позначками ✅ / ⬜
- **4 сторінки** по 10 категорій, навігація ◀️ / ▶️ та кнопка-індикатор `2/4`
- Позначки зберігаються при перегортанні сторінок
- Максимум **5 категорій** одночасно — більше означало б забагато RSS-запитів
  і занадто широке зведення. При спробі обрати шосту — спливаюче попередження
- Кнопка `▶️ Продовжити (N обрано)` з'являється тільки після вибору мінімум однієї
- Постійне меню внизу з'являється лише після підтвердження

Порядок списку визначає, що потрапить на першу сторінку: найпопулярніші мови
(`Python`, `Java`, `C++`, `NET`, `Node.js`, `Golang`, `Rust`) плюс `Front End`,
`AI/ML` і `Support`.

### Крок 2 — Меню пошуку

| Кнопка | Дія |
|--------|-----|
| 📅 Вакансії за 1 день | `days=1` — сьогодні та вчора |
| 📆 Вакансії за 7 днів | `days=7` |
| 📋 Всі вакансії | `days=None` — без обмеження по даті |
| 🔍 Вилучені з пошуку | Кількість вилучених + підтвердження показу |
| ⭐ Обране | Кількість обраних + підтвердження показу |
| 🔔 Сповіщення | Підписка на нові вакансії по обраних категоріях |
| 🗑 Очистити листування | Видаляє повідомлення, скидає категорії, повертає до кроку 1 |
| 🗑 Очистити список вилучених | Очищає список (або «📭 Список пустий») |

### Крок 3 — Звіт по джерелах, зведення та підтвердження

Після натискання кнопки періоду бот пише «⏳ Запрошую інформацію…» і надсилає
**один** рядок стану, який далі редагує на місці:

```
Djinni I ⏳ : Djinni II ⏳ : DOU I ⏳ : DOU II ⏳
Djinni I ⏳ : Djinni II ⏳ : DOU I 🔄 : DOU II ⏳
Djinni I ✅ : Djinni II ✅ : DOU I ❌ : DOU II ✅
```

`I` — Deftech, `II` — бронювання. Значки: `⏳` чекаємо, `🔄` повторна спроба,
`✅` успішно, `❌` вичерпані спроби.

Значки перемикаються **по одному**, з паузою `STATUS_STEP_SECONDS = 0.4` між
видимими змінами. Без неї фетч усіх джерел укладається приблизно в секунду і всі
значки перемкнулися б разом — людина просто не побачила б, що відбувалося.

Коли рядок стану стає повністю `✅`, дедуплікація (Етап 2) ще йде у фоновому
потоці. З тією ж паузою з'являється ще одне повідомлення — `🔀 Видалення
дублікатів…` — і після завершення редагується на місці: `🔀 Видалено 3
дублікати`. Через це підсумкове зведення нижче більше не показує кількість
дублікатів по кожному джерелу окремо — про це вже сказано одним повідомленням.

Джерел рівно чотири, але кожне опитується **для кожної категорії**: при двох
категоріях це вісім запитів. Тому `SourceProgress` зводить події за парою
(сайт, різновид) — значок стає підсумковим, коли по джерелу відзвітували всі
категорії, і успішним лише якщо жодна з них не впала.

Окремими повідомленнями лишаються тільки ті, що несуть інформацію, якої значок
не передає:

```
⚠️ DOU I джерело — Помилка, спроба 2/3
⏳ Почекай ще трошки, маємо затримку від джерела DOU I
```

Про повтор повідомляється **один раз на джерело**, а не на кожну категорію.

Якщо джерело мовчить довше за `SLOW_AFTER_SECONDS = 5` — приблизно середина
таймауту, — прилітає попередження із назвою джерела. Один раз на джерело:
людині досить знати, що затримка є і через кого, а не отримувати нагадування
щосекунди.

Фетч іде в робочому потоці, а сигналить із нього через `queue.Queue`
(потокобезпечну) — надсилає повідомлення вже цикл в основному потоці, де живе
Telegram-клієнт.



Показ розбитий на два кроки навмисно: генерація сотні картинок і сотня
`sendPhoto` — дорога операція, тож спершу користувач бачить лише текстове
зведення й вирішує, чи варто.

```
🗂 За останні 7 д. знайдено 42 вакансії, з них 5 в списку вилучених,
   до перегляду доступно 37 вакансій:

  • Python (з бронюванням) — 21 вакансія
  • Java (з бронюванням) — 16 вакансій

❓ Показати вакансії?
```

Три дії: `🔄 Переобрати категорії пошуку` / `❌ Ні` (→ «👍 Добре, почекаємо
оновлень!») / `✅ Так`.

> **Важливо:** вакансії завантажуються вже на кроці зведення й зберігаються в
> `chat_data["pending_vacancies"]`. Натискання `✅ Так` **не робить повторного
> запиту до RSS** — воно лише генерує картинки й розсилає картки.

### Крок 4 — Перегляд вакансій

Кожна вакансія — окреме повідомлення: картинка + підпис + інлайн-кнопки.
Порядок — **від найстаріших до найсвіжіших**, тож найновіша вакансія опиняється
найближче до поля вводу.

**Картинка** (800×300, Minecraft-стиль): темно-синій блок `#0F0F2D` із золотою
рамкою, назва вакансії по центру з товстою тінню.

- `Вакансія #N` — золотим у лівому верхньому куті
- `NEW` — біле на червоній плашці у правому верхньому куті (для ще не переглянутих)
- `* Обране *` — золотим у лівому нижньому куті

**Підпис** (HTML). Порожні поля пропускаються:

```
💼 Спеціальність: Senior Python Developer
🏢 Компанія: Acme Inc
📍 Місце роботи: Київ
💰 Зарплата: 5000 $
📅 Дата публікації: 20.07.2026
🌐 Фільтр: DOU (Deftech) Python
```

**Кнопки:** для DOU-вакансій зліва `🔎 Знайти` — пошук цієї ж вакансії на
Djinni через Google: `site:djinni.co inurl:jobs "<Спеціальність>" <Компанія>`,
справа `🔗 Відкрити` · `⭐ В обране` / `💛 В обраному` · `🙈 Не показувати`

Між картками витримується пауза `LIST_SEND_DELAY_SECONDS = 0.3` с: Telegram
притримує ботів, які сиплють в один чат без упину, а пачка легко буває на
кілька десятків карток — і при пошуку, і в годинному сповіщенні.

Пауза стосується **лише списків вакансій**. Відповіді на кнопки, редагування
карток і підсумкові рядки йдуть без затримки — там людина чекає реакції. Перед
**першою** карткою списку паузи теж немає.

### Система «Вилучені з пошуку»

- `🙈 Не показувати` → підпис картки **замінюється** на `🙈 Приховано: {назва}`,
  кнопки — на `👁 Відновити до перегляду`. Саме повідомлення не видаляється
- `👁 Відновити до перегляду` → картка відновлюється **на місці** (`editMessageMedia`)
  з повним підписом і початковими кнопками
- `🔍 Вилучені з пошуку` → спершу кількість + підтвердження, потім список карток
  з кнопкою відновлення під кожною
- Вилучені **не показуються** у наступних пошуках
- Список **персональний** і **персистентний** (SQLite)

Список вилучених показується лише для **обраних зараз категорій** — глобальний
список міг накопичитись, поки були обрані інші категорії, і показувати його
цілком було б несподівано.

### Система «Обране»

- `⭐ В обране` → вакансія потрапляє в персональний список, кнопка стає `💛 В обраному`
- Повторний клік → видаляє з обраного
- `⭐ Обране` → кількість + питання «Показати їх?» (`❌ Ні` → кнопка
  `🔄 Переобрати категорії пошуку`)
- У списку обраних кнопки інші: `🔗 Відкрити` · `💔 Прибрати з обраних` · `🙈 Не показувати`
- Список **персональний** і **персистентний** (SQLite)

### Сповіщення про нові вакансії

`🔔 Сповіщення` → екран із кнопкою `⚙️ Налаштувати сповіщення` → та сама
клавіатура категорій, але внизу `🔔 Додати нотифікацію (N обрано)`.

- Категорії сповіщень **окремі** від категорій пошуку: шукати руками можна одне,
  а отримувати сповіщення про інше. Тому клавіатура має власні `callback_data`
  (`ntf_toggle:` / `ntf_page:` / `notify_confirm`) — інакше один сценарій затирав
  би вибір іншого
- Ліміт той самий — до 5 категорій
- Проміжний вибір живе в `chat_data` як чернетка; у БД він потрапляє **лише**
  підтвердженим, тож наявна підписка не псується на півдорозі
- Підписка **персональна** й **персистентна** (`notification_subs`), разом із нею
  зберігається `chat_id`: шкедулер працює без апдейта, і взяти чат із
  `update.effective_chat` там немає звідки
- Повторне налаштування **переписує** список
- `🔕 Вимкнути сповіщення` спершу питає підтвердження («Сповіщення будуть
  вимкнені, а обрані категорії скинуті») — дія незворотна, а кнопка висить під
  кожним сповіщенням, тож випадкове натискання цілком імовірне. `✅ Так` видаляє
  підписку разом із журналом надісланого, `❌ Ні` повертає екран із кнопками

**Розсилка.** Щогодини з 8:00 до 20:00 (`Europe/Kyiv`) джоба збирає вакансії
**за поточну дату** й надсилає ті, яких людина ще не бачила сьогодні:

```
08:00  фід: A B      журнал: —        → надсилаємо A B, журнал := A B
09:00  фід: A B C    журнал: A B      → надсилаємо C,   журнал := A B C
10:00  фід: A B C    журнал: A B C    → нічого не надсилаємо
```

Журнал **накопичувальний**: якби з нього віднімали вже надіслане, вакансії
попередньої години наступного разу знову виглядали б новими. Живе в SQLite
(`notification_sent`), бо бот перезапускається на кожному деплої — список у
пам'яті означав би повтори. О 3:00 записи за попередні дні видаляються.

- **Один прохід на всіх**: категорії всіх підписників об'єднуються, фіди
  тягнуться один раз. Десять підписників на Python — один набір RSS-запитів
- **Чати обслуговуються паралельно** — `NOTIFY_CONCURRENCY = 8`. Усередині чату
  картки й далі йдуть послідовно з паузою: паралелимо саме різні чати. Вісім,
  бо картка коштує ~0.55 с (0.25 с `sendPhoto` + 0.3 с пауза), тобто один чат
  дає 1.8 повідомлення/с, а вісім — 14.5/с при глобальному ліміті Telegram
  ~30/с. На моделі: 100 підписників по 50 карток — 6 хв замість 46
- **Позначаємо кожну картку одразу після надсилання**, а не пачку в кінці: якщо
  Telegram обірве розсилку посередині (напр. flood control), доставлені картки
  лишаються в журналі й не приходять удруге наступної години
- Вилучені з пошуку не надсилаються; вакансія, що є в кількох обраних
  категоріях, приходить однією карткою
- Сповіщення **не чіпають мітку NEW** (`track_seen=False`) — інакше вони
  «з'їдали» б її для ручного пошуку
- Недоступний чат (бот заблокований) логується й не зупиняє розсилку решті
- Під кожним сповіщенням — кнопка `🔕 Вимкнути сповіщення`

### Мітка NEW

Вакансія вважається новою, якщо її хеш `(назва + компанія)` ще не потрапляв у
`bot_data["seen_{user_id}"]`. При першому перегляді NEW отримують усі.

### Очистити листування

Видаляє всі повідомлення діалогу (крім `/start`), скидає обрані категорії й
повертає до кроку 1.

**Переживає перезапуск бота.** Опорна точка (з якого повідомлення починати
видалення) зберігається в SQLite, тож після оновлення на сервері чи рестарту
`systemd` кнопка й далі прибирає всю історію, а не тільки те, що з'явилося
після перезапуску. Деталі — [нижче](#очищення-листування).

### Принципи

* **Шари.** `models` (домен) → `feeds` / `storage` / `images` (сервіси) →
  `bot` (Telegram). Залежності йдуть тільки згори вниз: сервіси нічого не знають
  про Telegram, домен — ні про що. Замінити Telegram на CLI чи веб можна, не
  чіпаючи `feeds/`.
* **Залежності передаються в конструктор.** Єдине місце, де створюються реальні
  об'єкти, — `BotApplication.__init__`; єдине місце, де читається оточення, —

* **Стан ізольований.** `UserState` / `ChatSession` — єдині місця, де формуються
  ключі `bot_data` / `chat_data`.
* **Один модуль — одна відповідальність.** Найбільший файл — 294 рядки.

## Домен: моделі та ідентифікатори

### `Vacancy` (`findmyjob/models.py`)

```python
@dataclass
class Vacancy:
    source: str = ""          # видима назва джерела → поле «🌐 Фільтр»
    title: str = ""           # посада
    link: str = ""            # повний URL вакансії
    published: str = ""       # рядок дати ("20.07.2026" або RFC 2822, або "невідомо")
    pub_dt: datetime | None = None
    company: str = ""
    location: str = ""        # місто, "Віддалено" або "в посиланні"
    salary: str = ""
    vacancy_hash: str = ""    # хеш (назва + компанія), заповнюється при парсингу
    category: str = ""        # напр. "Java", проставляється на етапі 1
```

**Усі поля мають значення за замовчуванням** — це не недбалість, а вимога:
вакансію треба вміти відновити з неповного словника (запис у «вилучених», що
зберігся ще до появи кешу, містить лише `title`).

| Член | Призначення |
|---|---|
| `short_link` | `make_link_hash(link)` — короткий ID для `callback_data` |
| `identity_hash` | `vacancy_hash` або обчислений на льоту — для мітки NEW |
| `publication_date()` | `date` для сортування й фільтрів; `None`, якщо дату не визначити |
| `to_dict()` | плаский словник — формат зберігання в `bot_data` та SQLite |
| `from_dict()` | **ігнорує сторонні ключі** — записи «вилучених» мають ще `categories`, якого немає серед полів моделі, тож звичайний `Vacancy(**data)` тут падав би |

### `MergedSource`

```python
@dataclass
class MergedSource:
    name: str                  # напр. "Python (з бронюванням)"
    vacancies: list[Vacancy]
    duplicates: int            # скільки прибрано на фінальному злитті
```

### Ідентифікатори

```python
make_vacancy_hash(title, company)  # SHA-256(f"{title.lower()}|{company.lower()}")[:16]
make_link_hash(link)               # SHA-256(link)[:16]
```

**Чому саме хеш повного посилання, а не `link[:50]`?** Telegram обмежує
`callback_data` 64 байтами, тож URL цілком туди не влазить. Але просто обрізати
його не можна: URL різних вакансій одного сайту часто збігаються в перших ~50
символах (спільний префікс компанії), а числовий ID вакансії йде вже **після**
50-го символу. Тобто різні вакансії буквально зливались в один `short_link`, і
приховування однієї ховало й іншу.

**Чому два різні хеші?** `link_hash` відповідає на питання «це та сама
публікація?» (для приховування, обраного, кешу), `vacancy_hash` — «це та сама
вакансія?» (для мітки NEW і злиття між сайтами, де URL завжди різні).

### Розбір дати

`publication_date()` пробує по черзі:

1. `pub_dt` — уже розпарсений `datetime` з RSS
2. `published` як `dd.mm.yyyy`
3. `published` як RFC 2822
4. `None` — дату визначити не вдалося

Вакансії з `None` **проходять** будь-який фільтр по даті (краще показати зайве,
ніж загубити) і сортуються **в кінець** списку.

## Підсистема фідів

### Категорії та джерела (`feeds/categories.py`)

Список категорій і DOU-слаги взяті з офіційного `<select name="category">` на
`jobs.dou.ua/vacancies/`. Три словники:

| Словник | Роль |
|---|---|
| `AVAILABLE_CATEGORIES` | 33 категорії в порядку показу |
| `DOU_CATEGORY_MAP` | категорія → слаг DOU (`NET` → `.NET`) |
| `DJINNI_KEYWORD_MAP` | категорія → ключове слово Djinni; `None` = джерел немає |

`DJINNI_KEYWORD_MAP["C-level"] is None` — для цієї категорії Djinni-джерела не
додаються взагалі: перевірено емпірично, адекватного відповідника немає, а
ключове слово дає лише шум.

```python
@dataclass(frozen=True)
class FeedSource:
    site: Site          # DOU | DJINNI
    variant: Variant    # DEFTECH | RESERVATION
    category: str
    url: str

    @property
    def name(self) -> str:      # "DOU (Deftech) Python"
        return f"{self.site.value} {self.variant.value} {self.category}"
```

`name` — не просто підпис: це те, що показується в полі «🌐 Фільтр» під кожною
вакансією. Раніше ці рядки склеювалися в чотирьох різних місцях; тепер вони —
похідна властивість одного типу.

### RSS-ендпоінти

Для кожної категорії — 4 (або 2, якщо Djinni-ключа немає):

```
DOU (Deftech) {кат}        → …/feeds/?category={слаг}&search=miltech, {слаг}
DOU (бронювання) {кат}     → …/feeds/?category={слаг}&search=бронювання, {слаг}
Djinni (Deftech) {кат}     → djinni.co/jobs/rss/?all_keywords={кл}&search_type=basic-search&editorial=miltech
Djinni (бронювання) {кат}  → djinni.co/jobs/rss/?all_keywords={кл}&search_type=basic-search&editorial=reservation
```

DOU поєднує **фільтр по категорії** з **пошуком двома термами через кому** —
формат узято з самої стрічки, яку DOU генерує для сторінки пошуку:
`?category=Java&search=бронювання, java`. Категорія лишається фільтром по
таксономії, а другим термом дублюється в запиті, як це робить сайт.

Значення параметрів екрануються: інакше `category=C++` сайт прочитав би як
`C` з двома пробілами.

Djinni шукає `search_type=basic-search` — по полях вакансії. `full-text`
пробували: він тягне забагато вакансій, що до запиту стосунку не мають, бо
ключове слово трапляється десь у тілі опису.

Приклад: 5 категорій → **20 паралельних HTTP-запитів** → 5 фінальних списків.

### `FeedFetcher` (`feeds/fetcher.py`)

```python
FeedFetcher(timeout=15, parser=EntryParser(), headers=DEFAULT_HEADERS)
    .fetch_all(sources) -> dict[FeedSource, list[Vacancy]]
    .fetch_one(source)  -> list[Vacancy]
```

- Джерело, що не відповіло, **пробується ще двічі** (`MAX_ATTEMPTS = 3`) з
  паузою `RETRY_DELAY_SECONDS = 7` між спробами. Вичерпані спроби → порожній
  список, а не виняток: одне впале джерело не валить усю вибірку. Таймаут
  запиту — 8 с, а не 15: інакше мертве джерело коштувало б 59 с очікування
  замість 38 (3×8 + 2×7)
- Усі фіди тягнуться **паралельно** через `ThreadPoolExecutor`, але не більше
  ніж `MAX_PARALLEL_FEEDS = 12` воркерів: без стелі пул дорівнював би кількості
  джерел, а для всіх 33 категорій це 130 потоків і стільки ж одночасних з'єднань
  до двох хостів. Саме 12, бо максимум ручного пошуку — 5 категорій = 20 джерел,
  тобто рівно дві хвилі (1.2 с проти 0.6 с без стелі; при 8 було б 1.8 с)
- HTTP-сесія **на потік** (`threading.local`) — інакше кожен фід починався б з
  нового TLS-хендшейка. Одна спільна сесія не годиться: `requests.Session` не
  гарантує потокобезпечності
- Помилка мережі на одному фіді → `logger.warning` і порожній список; решта
  джерел відпрацьовує нормально
- Підставляється браузерний `User-Agent` — обидва сайти віддають RSS охочіше
- Одразу після парсингу — дедуплікація **всередині фіду** за URL (той самий
  запис іноді приходить у RSS двічі)

### `VacancyFeedService` (`feeds/service.py`)

Публічний вхід у підсистему. Три етапи:

```
Етап 0   FeedFetcher → сирі Vacancy по кожному FeedSource
Етап 1   merge_by_link у межах сайту:
             Djinni (Deftech) + Djinni (бронювання) → CategoryFeeds.djinni
             DOU (Deftech)    + DOU (бронювання)    → CategoryFeeds.dou
         ── кешується на 120 с, БЕЗ фільтру по даті ──
Фільтр   _passes_date() на обох списках
Етап 2   merge_by_title_and_company(dou, djinni) → MergedSource
```

**Чому фільтр по даті стоїть саме між етапами, а не раніше?**
Якби дублікати рахувалися до обрізання по даті, у зведенні могло б з'явитися
«видалено 8 дублікатів» під рядком «2 вакансії» — бо частину відфільтрувала
дата вже після підрахунку. Тепер `MergedSource.duplicates` завжди узгоджений з
тим, що реально показано.

**Чому кешується саме етап 1?** Кеш зберігає «всечасовий» знімок фіду, тому
один мережевий похід обслуговує всі три часові вікна (1 день / 7 днів / весь
час). Перемикання періодів у межах 2 хвилин не робить жодного HTTP-запиту.

```python
class _Stage1Cache:      # потокобезпечний TTL-кеш
    key   = tuple(sorted(categories))
    value = (time.monotonic(), {категорія: CategoryFeeds})
```

## Парсинг

`EntryParser.parse(entry, source) -> Vacancy` — оркестратор. Порядок важливий:

```
1. дата           parsedate_to_datetime(entry.published)
2. заголовок      parse_dou_title(entry.title) → (title, company, salary, location)
3. компанія       parsed.company  або  extract_company(...)
4. локація        parsed.location або  extract_location(...)   ← лише для Djinni
5. хеш            make_vacancy_hash(title, company)
```

**DOU-формат заголовка пробується для всіх джерел**, бо Djinni теж інколи
віддає заголовки виду «Посада в Компанія». А от парсинг `<description>` —
**лише для Djinni**: у DOU вся інформація вже в `<title>`, і копання в описі там
дає хибні спрацювання.

### Розбір DOU-заголовка (`parsing/dou_title.py`)

DOU пакує всю вакансію в один рядок:

```
"Senior Python Developer в Acme Inc, $5000, Київ"
 └── посада ──────────┘   └ компанія ┘ └зп┘ └місто┘
```

Алгоритм:

1. Знайти **найраніший** роздільник із ` в `, ` на `, ` у `. Немає — весь рядок
   вважається посадою
2. Якщо залишок містить маркери опису (`«ми шукаємо»`, `«обов'язки»`,
   `«вимоги»`, `«пропонуємо»`…) — це не компанія, а початок опису → одразу
   шукати компанію за **наступним** роздільником
3. Розкласти частини після коми на `company` / `salary` / `location`:
   зарплату розпізнає `SALARY_RE` (`$`, `€`, `£`, `грн`, «від», діапазони, `тис`/`k`)
4. Витягти зарплату, що злиплася з назвою компанії
5. Відділити міста від назви (`split_company_and_cities`)
6. Якщо компанія не пройшла валідацію — повторити пошук за наступним роздільником
7. Обрізати хвіст-слоган: `«HostZealot — хостинг, якому довіряють»` → `«HostZealot»`

`split_company_and_cities("Acme Inc, Київ, Львів")` → `("Acme Inc", "Київ, Львів")`.
Місто розпізнається евристично: коротше 25 символів, без цифр, без ознак
зарплати, не закінчується на `:`. Ідемо з кінця, поки частини схожі на міста.

> **Нюанс.** Коли компанія знайдена за другим роздільником, а хвоста після неї
> немає — `salary` і `location`, здобуті основним розбором, **зберігаються**, а
> не затираються порожніми.

### Валідація компанії (`parsing/company.py`)

RSS Djinni не має окремого поля з компанією — її доводиться діставати з
HTML-опису. Тому основна складність не «витягти», а «зрозуміти, що витягли не
те». `is_invalid_company()` відкидає кандидата, якщо він:

| Перевірка | Приклад хибного кандидата |
|---|---|
| Закінчується на `: , . ? !` | `«Про компанію:»` |
| Довший за 60 символів | абзац опису |
| Більше 5 слів | речення |
| Містить `/` | `«Hardware, Software та MilTech/IoT»` |
| Число + одиниця часу | `«5 років»`, `«3 years»` |
| Починається зі службового слова | `«Ваша роль»`, `«What we offer»`, `«Наша команда»` |
| Дублює назву посади | title=`«CRM / Workflow Administrator»`, кандидат=`«Senior CRM & Workflow Administrator»` |
| Точний збіг із заголовком секції | `«Requirements»`, `«Про нас»` |
| Містить маркер опису | `«ми шукаємо»`, `«цінності»`, `«якому довіряють»` |

**Велика літера.** Назву компанії завжди пишуть з великої, тож кандидат, що
починається з малої, — це уривок опису (`вже 25 років`, `лідери ринку`). Цифри
й лапки на початку допустимі: `«Промавтоматика»`, `414 окрема бригада`. Правило
спільне для Djinni- і DOU-валідаторів. Ціна — бренди, писані з малої (`monobank`,
`eBay`), лишаться без назви; порожнє поле краще за уривок тексту.

Перевірка на дублювання назви посади робиться в три способи: повний збіг,
збіг перших двох слів і **перекриття значущих слів ≥ 60 %** (слова від 3
символів, без пунктуації).

**Нормалізація гомогліфів.** Назви компаній часто пишуть змішаною кирилицею й
латиницею (`СoreTech`, де `С` — кирилична). Перед порівнянням 26 таких
літер-двійників переводяться в латиницю, інакше `«Сore»` і `«Core»` виглядали б
різними рядками. Ця ж нормалізація використовується в ключі дедуплікації
(див. [«Дедуплікація»](#дедуплікація)).

**Витягування з опису** — дві стратегії за пріоритетом:

1. **Дієслово-маркер:** `«<Назва> розробляє / шукає / займається / спеціалізується…»`.
   Кожен `<p>` обробляється окремо, щоб не захопити текст сусіднього абзацу.
   Кандидати з самих лише займенників (`«Ми розробляємо»`) відкидаються
2. **Назва в лапках:** `«Промавтоматика»`, `"Ajax Systems"` — найнадійніший
   сигнал, тому лапки входять у клас символів патерна з дієсловом. Без них у
   `«група компаній «Промавтоматика» вже 25 років працює»` збіг починався б
   після закривальної лапки й давав `«вже 25 років»`
3. **Вступний патерн:** `«<Назва> — опис»` або `«<Назва> is a/an/the …»`, але
   **лише на початку абзацу** й **лише серед перших трьох абзаців**. Вступ про
   компанію завжди йде на самому початку; якщо шукати по всьому тексту, той
   самий патерн (тире, дієслово «is») трапляється в будь-якому реченні всередині
   опису й дає хибні збіги
4. **Привітання:** у `«Привіт! Ми — Moodro»` назва стоїть **праворуч** від тире,
   а не ліворуч. Спрацьовує лише коли ліворуч самі привітання та займенники, і
   лише якщо праворуч слово з великої літери: це те, що відрізняє `Moodro` від
   `«Вони — лідери ринку»`

`is_invalid_dou_company()` — окрема, **м'якша** версія: без обмеження на
кількість слів і з лімітом 100 символів. Офіційні назви військових частин
бувають довгими: `«414 окрема бригада безпілотних систем "Птахи Мадяра"»`.

### Визначення міста (`parsing/location.py`)

Словник `CITY_FORMS` відмінкових форм (15 міст) — пошук у `title + description`:

```python
"києві" / "київ"             → "Київ"
"кривому розі" / "кривий ріг" → "Кривий Ріг"
```

Ключі перебираються **за спаданням довжини**, щоб `«кривому розі»` перевірилось
раніше за коротші форми. Окремо розпізнається
`«формат роботи: віддалено»` → `"Віддалено"`. Не знайдено → `"в посиланні"`:
місто в описі є не завжди, і відсилання до самої вакансії корисніше за «немає».

## Дедуплікація

Дублікати ловляться на **трьох рівнях**, і на кожному «однакова вакансія»
означає різне:

| Рівень | Де | Ключ | Чому саме такий |
|---|---|---|---|
| 0 | всередині одного фіду | повний URL | той самий запис іноді приходить у RSS двічі |
| 1 | у межах сайту ((Deftech) + (бронювання)) | повний URL | та сама вакансія має буквально той самий URL |
| 2 | між сайтами (DOU + Djinni) | `(dedup_key(title), dedup_key(company))` | різні сайти → різні URL навіть для однієї вакансії, порівнювати їх марно |

```python
merge_by_link(name, primary, secondary) -> MergeResult
merge_by_title_and_company(name, primary, secondary) -> MergeResult
```

При збігу запис видаляється з **secondary**. На етапі 2 primary — це DOU, тобто
**DOU має пріоритет** над Djinni.

**Нормалізація ключа** (`dedup_key`). Сирі рядки для порівняння не годяться:
одну й ту саму вакансію DOU і Djinni пишуть по-різному. Тому перед звірянням і
назва, і компанія проходять через нормалізацію:

```
"Інженер з підтримки систем | СЕВ ОВВ"   (DOU)
"Інженер з підтримки систем / СЕВ ОВВ"   (Djinni)
        ↓ гомогліфи → латиниця, роздільники → пробіл, стиснути пробіли, lower
"іhжehep з підtpиmkи cиctem ceb obb"     ← однаковий ключ, дублікат знайдено
```

- роздільники `| / \ — – − - , ; · •` → пробіл: та сама вакансія на двох сайтах
  часто відрізняється **лише** ними
- кириличні літери-двійники → латиниця (`СЕВ` проти `CEB`)
- типографські апострофи, `NBSP` і повторні пробіли — до канонічного вигляду

Крапки, плюси, решітки й дужки навмисно **не** чіпаються: саме вони відрізняють
`C++` від `C#`, `.NET` від `NET` і `(React)` від `(Vue)`.

**Правила етапу 2** (`_TitleCompanyIndex`):

- Є і `title`, і `company` → порівняння по парі
- `company` порожній → порівняння лише по `title`, причому і зі списком
  «title з компанією», і зі списком «title без компанії»
- `title` порожній → **ніколи не дедуплікується**, завжди залишається

Індекс зберігає не ключ, а саму вакансію — щоб при виявленні дубліката
залогувати **обидва** записи з посиланнями.

## Сховище

`VacancyStore` (`findmyjob/storage.py`) — SQLite, файл `bot_storage.db`.

```python
store.init_db()                          # CREATE TABLE IF NOT EXISTS ×5

store.replace_hidden(user_id, data)      # data: {short_link: {...}}
store.replace_favorites(user_id, data)
store.load_all_hidden()    -> {user_id: {short_link: {...}}}
store.load_all_favorites() -> {user_id: {short_link: {...}}}

store.save_chat_anchors(chat_id, ChatAnchors(...))
store.load_chat_anchors(chat_id) -> ChatAnchors

store.save_subscription(user_id, chat_id, categories)
store.delete_subscription(user_id)
store.load_all_subscriptions() -> {user_id: NotificationSub}

store.sent_today(user_id, day)   -> {short_link}
store.mark_sent(user_id, day, short_links)
store.purge_sent_before(day)     # нічне прибирання
store.clear_sent(user_id)        # при вимкненні сповіщень
```

П'ять таблиць. `hidden` і `favorites` — однакової схеми:

```sql
CREATE TABLE IF NOT EXISTS hidden (
    user_id      INTEGER NOT NULL,
    short_link   TEXT    NOT NULL,
    title        TEXT    NOT NULL DEFAULT '',
    source       TEXT    NOT NULL DEFAULT '',
    link         TEXT    NOT NULL DEFAULT '',
    published    TEXT    NOT NULL DEFAULT '',
    pub_dt       TEXT,                          -- ISO-8601 або NULL
    company      TEXT    NOT NULL DEFAULT '',
    location     TEXT    NOT NULL DEFAULT '',
    salary       TEXT    NOT NULL DEFAULT '',
    vacancy_hash TEXT    NOT NULL DEFAULT '',
    category     TEXT    NOT NULL DEFAULT '',
    categories   TEXT    NOT NULL DEFAULT '[]', -- JSON-масив
    PRIMARY KEY (user_id, short_link)
);
```

**Стратегія запису — «повна заміна на користувача».** Кожна зміна робить
`DELETE WHERE user_id = ?` + `executemany INSERT`. Списки маленькі (десятки
записів), а натомість неможливий розсинхрон між пам'яттю та БД: у таблиці
завжди рівно те, що в `bot_data`.

Третя таблиця — `chat_state`, опорні точки для «Очистити листування»:

```sql
CREATE TABLE IF NOT EXISTS chat_state (
    chat_id                  INTEGER PRIMARY KEY,
    first_tracked_message_id INTEGER,   -- нижня межа діапазону видалення
    start_message_id         INTEGER    -- якір /start, переживає очищення
);
```

```python
@dataclass(frozen=True)
class ChatAnchors:
    first_tracked_message_id: int | None = None
    start_message_id: int | None = None
```

Запис — через `INSERT ... ON CONFLICT(chat_id) DO UPDATE`, тобто один рядок на
чат. Детальніше про те, чому двох чисел достатньо, — у розділі
[«Очищення листування»](#очищення-листування).

Четверта — `notification_subs`, підписки на сповіщення:

```sql
CREATE TABLE IF NOT EXISTS notification_subs (
    user_id    INTEGER PRIMARY KEY,   -- підписка на користувача рівно одна
    chat_id    INTEGER NOT NULL,      -- куди слати; шкедулер працює без апдейта
    categories TEXT    NOT NULL,      -- JSON-масив
    created_at TEXT
);
```

П'ята — `notification_sent`, журнал надісланого за день:

```sql
CREATE TABLE IF NOT EXISTS notification_sent (
    user_id    INTEGER NOT NULL,
    day        TEXT    NOT NULL,   -- YYYY-MM-DD, робить очищення тривіальним
    short_link TEXT    NOT NULL,
    PRIMARY KEY (user_id, day, short_link)
);
```

Первинний ключ робить повторне надсилання неможливим за побудовою.

**Міграція не потрібна.** `init_db()` виконує `CREATE TABLE IF NOT EXISTS` для
всіх п'яти таблиць і є ідемпотентним: на наявній БД він лише додає нові,
не чіпаючи `hidden` і `favorites`.

**Увімкнено WAL** (`PRAGMA journal_mode = WAL`) — читання не блокує запис.

**Персистентно зберігається лише необхідний мінімум.** Кеш показаних вакансій,
seen-хеші й обрані категорії живуть тільки в пам'яті процесу й свідомо
скидаються при перезапуску: це похідні дані, які дешево відновити. А от опорні
точки чату відновити нізвідки — Telegram не віддає історію повідомлень, — тому
вони в БД.

`categories` — це **JSON-масив** усіх категорій, у яких бот бачив цю вакансію
(не те саме, що `category` — категорія на момент першого показу). Див.
[самозцілення](#самозцілення-категорій-у-вилучених).

## Telegram-шар

### `BotApplication` (`bot/application.py`)

Кореневий об'єкт: тут і **тільки тут** створюються реальні залежності.

```python
BotApplication(Settings.from_env()).run()
```

| Метод | Дія |
|---|---|
| `__init__` | створює `VacancyStore`, `StateRepository`, `VacancyFeedService`, `VacancyImageRenderer`, `VacancySender` і шість груп обробників |
| `build()` | `init_db()`, підвантаження БД у `bot_data`, реєстрація обробників |
| `run()` | `build()` + `run_polling()` |
| `_preload_state()` | один раз читає обидві таблиці й розкладає по ключах `bot_data` |

### Групи обробників

Кожна група — клас-нащадок `HandlerGroup`, що сам оголошує свої обробники через
`handlers()`. Додати сценарій = додати клас і згадати його в `BotApplication`.

| Клас | Сценарій | Обробники |
|---|---|---|
| `CategoryHandlers` | вибір категорій | `/start`, `toggle`, `change_page`, `noop`, `confirm`, `reselect` |
| `VacancyHandlers` | пошук і показ | `request_from_message`, `show_1d`, `show_14d`, `confirm_show`, `decline_show` |
| `HiddenHandlers` | вилучені | `hide`, `unhide`, `restore`, `show_prompt`, `show_list`, `clear` |
| `FavoriteHandlers` | обране | `add`, `remove`, `delete_from_list`, `show_all`, `decline_show`, `send_prompt` |
| `MaintenanceHandlers` | обслуговування | `clear_history`, `clear_chat`, `track_user_message` |
| `MenuHandlers` | нижнє меню | маршрутизація за текстом кнопки |

### Порядок реєстрації

PTB виконує **лише один** обробник на групу (перший, що збігся), тому порядок
має значення:

1. `CommandHandler("start")`
2. Усі `CallbackQueryHandler` — патерни не перетинаються, порядок між ними
   несуттєвий
3. `MessageHandler(TEXT & Regex(кнопки меню))`
4. `MessageHandler(filters.ALL)` — «усе інше», лише запам'ятовує ID повідомлення

Пункт 4 обов'язково останній: інакше він перехоплював би натискання кнопок меню.

### `callbacks.py`

`callback_data` обмежена 64 байтами, тому ідентифікатори короткі, а замість
посилання їде його хеш.

```python
payload(CB_HIDE, short_link)   # "hide:a1b2c3d4e5f6a7b8"
argument(query.data, CB_HIDE)  # "a1b2c3d4e5f6a7b8"
exact(CB_NOOP)                 # "^noop$"       — дії без параметрів
prefixed(CB_HIDE)              # "^hide:"       — дії з параметром
```

Патерни-префікси не конфліктують: `^fav:` не збігається з `fav_del:…`,
`^hide:` — з `unhide:…`.

### `VacancySender` (`bot/sending.py`)

Єдине місце, де вакансія перетворюється на повідомлення. На кожну вакансію:

1. `Vacancy.from_dict(data)`
2. визначає `is_new` (хеш не в `seen`) і `is_favorite`
3. **кладе повні дані в `vacancy_cache`** — щоб наступні `hide` / `fav` /
   `restore` не тягли RSS заново
4. рендерить картинку, форматує підпис, будує клавіатуру
5. `chat.send_photo(...)`

Наприкінці — один раз оновлює `seen` усіма новими хешами.

### Форматування (`bot/formatting.py`, `bot/texts.py`)

`pluralize_ua(n, one, few, many)` — українські правила відмінювання числівників:

```
1, 21, 31…  (крім 11)  → «вакансія»
2-4, 22-24…            → «вакансії»
0, 5-20, 25-30…        → «вакансій»
```

Використовується для «вакансія/вакансії/вакансій», «дублікат/дублікати/
дублікатів» і «обрану вакансію / обрані вакансії / обраних вакансій».

`clean_salary()` прибирає прийменник «від» **лише коли це не діапазон**:
`«від 2000–3000 грн»` читається як діапазон і без нього, а от `«від 2000»` без
прийменника втратило б сенс.

Усі підписи проходять `html.escape()` — назви вакансій із `<`, `>`, `&` інакше
ламали б HTML parse mode.

## Стан і структури даних

| Ключ | Тип | Зміст | Персистентність |
|------|-----|-------|:---:|
| `bot_data["hidden_{uid}"]` | `dict[str, dict]` | `{short_link: {…поля вакансії, categories: [...]}}` | SQLite |
| `bot_data["favorites_{uid}"]` | `dict[str, dict]` | `{short_link: {…поля вакансії}}` | SQLite |
| `bot_data["vcache_{uid}"]` | `dict[str, dict]` | Кеш повних даних показаних вакансій | у пам'яті |
| `bot_data["seen_{uid}"]` | `set[str]` | Хеші переглянутих вакансій (мітка NEW) | у пам'яті |
| `bot_data["categories_{uid}"]` | `list[str]` | Обрані категорії пошуку | у пам'яті |
| `bot_data["notify_{uid}"]` | `list[str]` | Категорії підписки на сповіщення | **SQLite** |
| `chat_data["first_tracked_message_id"]` | `int \| None` | Нижня межа діапазону очищення | **SQLite** |
| `chat_data["start_message_id"]` | `int \| None` | ID повідомлення `/start` (якір) | **SQLite** |
| `chat_data["pending_vacancies"]` | `list[dict]` | Вибірка між зведенням і показом | у пам'яті |
| `chat_data["cat_page"]` | `int` | Поточна сторінка вибору категорій | у пам'яті |
| `chat_data["notify_draft"]` | `list[str]` | Чернетка вибору категорій сповіщень | у пам'яті |
| `chat_data["anchors_loaded"]` | `bool` | Прапорець лінивої гідратації з БД | службовий |

Доступ до цих ключів інкапсульовано у двох класах (`bot/state.py`) — напряму до
`bot_data` / `chat_data` більше ніхто не звертається:

```python
class UserState:      # per-user, ключі bot_data
    hidden / favorites / vacancy_cache / seen / categories
    save_hidden() / save_favorites()          # bot_data + SQLite одним викликом
    hidden_for_categories(cats)
    cache_vacancy() / cached_vacancy()
    mark_seen(hashes) / set_categories(cats)

class ChatSession:    # per-chat, ключі chat_data
    track(*ids)                               # опускає нижню межу діапазону
    first_tracked_message_id / forget_tracked()
    start_message_id                          # сеттер одразу пише в SQLite
    category_page
    pending_vacancies / clear_pending()
```

`StateRepository` — фабрика: єдиний об'єкт, що знає про `VacancyStore`.
`chat(update, context)` бере `chat_id` з `update.effective_chat`, бо сам
`context.chat_data` свого ID не знає.

**Лінива гідратація.** `ChatSession.__init__` при першому зверненні до чату
читає опори з БД у `chat_data` і ставить прапорець `anchors_loaded`. Так ми
не завантажуємо всі чати на старті — а PTB і не дав би: `Application.chat_data`
віддається як read-only проксі, записати в нього ззовні неможливо.

## Генерація картинок

зсувом `(3,3)`, `(3,0)`, `(0,3)` кольором `#502800`, і зверху — основний.

## Ключові інваріанти та неочевидні рішення

### Два кроки замість одного

Між «завантажити» і «показати» стоїть підтвердження, бо це принципово різні за
ціною операції: перша — 20 паралельних HTTP-запитів, друга — генерація сотні
PNG і сотня `sendPhoto`. Вибірка живе в `chat_data["pending_vacancies"]`, тож
`✅ Так` не робить повторного походу в мережу.

### Три рівні кешування

| Що | Де | Навіщо |
|---|---|---|
| Етап 1 фідів, 120 с | `_Stage1Cache` | перемикання періодів не робить HTTP-запитів |
| `pending_vacancies` | `chat_data` | зведення → показ без ре-фетчу |
| `vcache_{uid}` | `bot_data` | `hide` / `fav` / `restore` без ре-фетчу |

### Самозцілення категорій у вилучених

Категорії між собою **не дедуплікуються**: та сама вакансія може знайтися
одразу в `Python` і в `DevOps`. Якщо користувач приховав її, шукаючи по
`Python`, у записі буде `categories: ["Python"]` — і при пошуку по `DevOps`
список «вилучених» її б не показав.

Тому при кожному пошуку бот дописує в `hidden[short_link]["categories"]` ту
категорію, у якій щойно натрапив на вакансію, і зберігає зміну в БД. Список
поступово стає точним сам собою.

### Підрахунок вилучених — за унікальними ID

З тієї ж причини кількість вилучених рахується як **множина `short_link`**, а
не як «було мінус стало». Та сама вакансія, знайдена у двох категоріях,
задвоїла б лічильник.

### Порядок сортування

Найстаріші зверху, найсвіжіші — останнім повідомленням. У Telegram список
гортається вниз, тож найновіша вакансія опиняється найближче до поля вводу.
Ключ сортування — `(дата невідома?, дата)`, щоб вакансії без дати йшли в
кінець, а не помилково на початок (як було б із `date.min`).

### Запасні шляхи після перезапуску

Кеш вакансій живе в пам'яті, тож після рестарту бот може отримати `hide` або
`fav` на вакансію, про яку вже нічого не знає. Передбачено два рівні
(опорні точки очищення сюди не належать — вони в БД, див.
[«Очищення листування»](#очищення-листування)):

- `hide` / `fav` — назва витягується **з підпису вже надісланого повідомлення**
  (рядок із `«Спеціальність:»`)
- `unhide` / показ обраних — робиться **живий фетч** усіх категорій, і вакансія
  шукається по `short_link`

### Обмеження на 100 вакансій з джерела

`MAX_PER_SOURCE = 100` застосовується **після** прибирання вилучених — інакше
приховані вакансії з'їдали б ліміт і витісняли ті, які користувач іще не бачив.

### Очищення листування

Telegram не дає API «список повідомлень чату», тож бот іде **суцільним
діапазоном ID** від найранішого відстеженого до поточного. Те, що видалити не
вдалося (чуже повідомлення або старше за 48 годин — ліміт Bot API), просто
пропускається. Повідомлення `/start` зберігається як якір і не видаляється.

**Стан — це два числа, а не список.** Якщо видалення все одно йде суцільним
діапазоном, то з усього переліку надісланих повідомлень насправді потрібна лише
його **нижня межа**. Тому `track()` не накопичує ID, а лише опускає межу:

```python
def track(self, *message_ids):
    lowest = min(message_ids)
    if current is None or lowest < current:
        self._chat_data[KEY_FIRST_TRACKED] = lowest
        self._save_anchors()
```

Це дає три речі одразу:

1. **Персистентність стає тривіальною** — два `INTEGER` на чат замість списку,
   що росте
2. **Зникає витік пам'яті** — раніше `chat_data["message_ids"]` накопичував ID
   кожного колись надісланого повідомлення і ніколи не звільнявся
3. **Запис у БД стає рідкісним** — межа змінюється лише коли вона реально
   опускається

Виміряно: **200 повідомлень діалогу → 2 записи в БД**; цикл очищення → ще 2
(скидання межі + нова клавіатура категорій). Звичайне надсилання картки вакансії
в БД не пише взагалі.

**Що відбувається при перезапуску.** `chat_data` порожній, але при першому ж
зверненні до чату `ChatSession` підтягує опори з `chat_state`. Тому кнопка
бачить повідомлення, надіслані ще до рестарту:

```
Запуск 1:  /start=101 → якір=102, далі повідомлення 103…107
──────────── рестарт бота (chat_data очищено) ────────────
Запуск 2:  якір=102 відновлено з БД, нові повідомлення 110…113
Очищення:  видаляє 102…113, пропускає /start=101
           новий якір=114 → одразу в БД
```

Повторне очищення після другого рестарту почнеться вже з `114` — вдруге по
видалених ID бот не ходить.

### Блокуючий I/O

Мережеві походи виконуються через `asyncio.to_thread(...)`, щоб не блокувати
event loop PTB. Усередині `FeedFetcher` — свій `ThreadPoolExecutor` на всі фіди.

### Мертві callback-обробники

`CB_VAC_1D` / `CB_VAC_14D` не породжуються жодною поточною клавіатурою, але
обробники зареєстровані навмисно: у користувачів у чатах могли лишитися старі
повідомлення з такими кнопками.

## Конфігурація

`Settings` (`findmyjob/config.py`) — єдине місце, де читається оточення.

| Параметр | За замовч. | Роль |
|---|---|---|
| `bot_token` | з `.env` | обов'язковий; без нього — `RuntimeError` при старті |
| `db_path` | `bot_storage.db` | файл SQLite |
| `request_timeout` | `15` | таймаут одного RSS-запиту, с |
| `cache_ttl_seconds` | `120` | TTL кешу етапу 1 |
| `max_vacancies_per_source` | `100` | ліміт показу на джерело |

Константи інтерфейсу живуть поруч зі своїм кодом:
`CATEGORIES_PER_PAGE = 10`, `MAX_SELECTED_CATEGORIES = 5` (`bot/keyboards.py`).

## Розгортання

**systemd** (`deploy/findmyjob-bot.service`) — автозапуск і `Restart=always`:

```ini
ExecStart=/home/ubuntu/FindMyJob/.venv/bin/python bot.py
Restart=always
RestartSec=5
```

**CI/CD** (`.github/workflows/deploy.yml`) — push у `master` → SSH на Oracle
Cloud → `git pull` → `pip install -r requirements.txt` → `systemctl restart`.

```bash
sudo systemctl status findmyjob-bot
journalctl -u findmyjob-bot -f
```

> `.env` і `bot_storage.db` у `.gitignore` — токен і персональні дані
> користувачів у репозиторій не потрапляють.
