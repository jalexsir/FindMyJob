# Контекст для наступної сесії

Файл для нового чату, який починає з нуля: що вже вирішено й **чому**, які
пастки в середовищі, що лишилось у роботі. Технічний опис самого проєкту — у
[README.md](README.md), тут лише те, чого в ньому немає.

Останнє оновлення: 31.07.2026, `master` на `ef437ec` (PR #21).

## 1. Як ми працюємо

- **Мова спілкування — українська.** Коміти, PR і коментарі в коді теж.
- **Гілка на зміну**, назва `claude/<суть>`. Прямо в `master` не комітимо.
- **Кожна зміна → PR → мерж** після явного «+» від користувача (домовлено
  02.08.2026 — раніше було «так», тепер саме «+»). PR-опис містить проблему,
  рішення, причини й те, як перевірено.
- **Мерж запускає деплой.** `.github/workflows/deploy.yml` по SSH заходить на
  Oracle, робить `git pull`, `pip install -r requirements.txt` і
  `systemctl restart findmyjob-bot`. Про ручний деплой писати не треба.
- Після мержу — `git pull` у локальний `master` і видалення злитої гілки.
- **Анонс релізу адміну (`CHANGELOG_PENDING.md`).** Якщо PR вартий анонсу,
  перед запитом «+» СПЕРШУ показати чернетку тексту релізу (версія + пункти)
  користувачу в чаті й дочекатись підтвердження — лише тоді текст іде у
  файл і питається «+» на мерж. Формат і механізм — README §«Сповіщення
  адміну про оновлення».

| Що | Деталі |

| **Інші залежності** | `pip install python-telegram-bot pillow python-dotenv APScheduler`; системна `cryptography` конфліктує з `cffi` — лікується `pip install --upgrade cffi` |

| **Тестів у репозиторії немає** | Перевірка — одноразові скрипти в scratchpad, які **гинуть разом із контейнером**. Це відомий борг, див. §6 |

Запуск перевірок: `python -m pyflakes findmyjob bot.py` (єдиний лінтер, що є).

## 3. Сервер

- Oracle Cloud Always Free, `VM.Standard.E2.1.Micro`: **1 OCPU, 1 ГБ RAM**, без
  swap. Це реальне обмеження — див. заміри в §5.
- **Час на сервері — UTC.** Київський = +3. `journalctl --since "19:00"` означає
  19:00 **UTC**; надійніше `--since "2 hours ago"`.
- Логи: `journalctl -u findmyjob-bot`. Імена логерів латиницею, тож грепати
  краще по них, а не по кирилиці:
  - `findmyjob.feeds.fetcher` — пише **тільки при помилці** завантаження
  - `findmyjob.bot.notifier` — прогони розсилки
  - `findmyjob.bot.application` — старт, реєстрація джоб
- `httpx` приглушено до WARNING (інакше рядок на кожен `getUpdates` топив усе).

## 4. Ухвалені рішення та їх причини

Щоб не переробляти по колу — тут те, що вже пробували й свідомо обрали.

### Джерела й пошук

- **Djinni: `search_type=basic-search`.** `full-text` пробували (PR #15-#17) —
  тягне забагато нерелевантного, слово трапляється десь у тілі опису. Відкотили.
- **DOU: `?category={слаг}&search={варіант}, {слаг}`**, без `descr=1`. Формат
  узято з живої стрічки, яку DOU генерує для сторінки пошуку. `descr=1` теж
  пробували — виміряно, що він додає лише одну вакансію, у стрічках DOU його
  немає.
- **Значення параметрів екрануються.** Раніше `category=C++` сайт читав як «C» з
  двома пробілами — пошук по C++ увесь час ішов не по тій категорії.
- **4 запити на категорію** (DOU/Djinni × Deftech/бронювання). Виняток —
  `C-level`, для нього немає Djinni-ключа, тому 2.

### Парсинг компанії (Djinni бере її з опису)

- Кандидат **з малої літери** — це уривок опису, а не назва. Правило спільне для
  Djinni й DOU. Цифри й лапки на початку допустимі (`414 окрема бригада`,
  `«Промавтоматика»`). Ціна: бренди на кшталт `monobank` лишаться без назви — це
  свідомо, порожнє поле краще за уривок.
- Патерни, що вже ловляться: `<Назва> розробляє/шукає/…`, `<Назва> — опис`,
  `<Назва> is a…`, назва в лапках, і **назва праворуч від тире** після
  привітання (`Привіт! Ми — Moodro`).

### Дедуплікація

- Ключ — **нормалізована** пара (назва, компанія): роздільники `| / \ — – − - ,
  ; · •` → пробіл, кириличні гомогліфи → латиниця, апострофи й NBSP до
  канонічного вигляду, `lower`. Крапки, плюси, решітки й дужки **не чіпаємо** —
  саме вони відрізняють `C++` від `C#`, `.NET` від `NET`, `(React)` від `(Vue)`.
- «Lead X» і «Senior X» від однієї компанії — **не дублікати**. Це різні
  вакансії, склеювати не треба (перевіряли за скаргою, виявилась хибна тривога).

### Сповіщення

- Категорії сповіщень **окремі** від категорій пошуку, з власними `callback_data`
  (`ntf_*`), інакше сценарії затирають вибір один одного.
- Журнал надісланого **накопичувальний** і в SQLite. Якщо віднімати надіслане,
  вакансії попередньої години наступного разу знову виглядають новими. У пам'яті
  тримати не можна — бот перезапускається на кожному деплої.
- Позначаємо кожну картку **одразу після надсилання**, а не пачку в кінці:
  обрив посередині інакше означав би повтор усієї пачки.
- Сповіщення **не чіпають мітку NEW** (`track_seen=False`).
- Коли нових вакансій немає — **нічого не шлемо** (раніше було повідомлення
  «На зараз не знайдено нових вакансій» з кнопкою щогодини — забирало чат,
  прибрано).

### Числа й чому саме такі

| Константа | Значення | Чому |
|---|---|---|
| `MAX_PARALLEL_FEEDS` | 12 | 5 категорій = 20 джерел = рівно 2 хвилі (1.2 с проти 0.6 с без стелі; при 8 було б 1.8 с). Без стелі — 130 потоків на 1 OCPU |
| `MAX_ATTEMPTS` / `RETRY_DELAY_SECONDS` | 3 / 7 с | мертве джерело коштує 3×8 + 2×7 = 38 с |
| `request_timeout` | 8 с | було 15 — з повторами давало 59 с очікування |
| `NOTIFY_CONCURRENCY` | 8 | 1.8 повідомл./с на чат × 8 = 14.5/с при ліміті Telegram ~30/с. 100 підписників × 50 карток: 6 хв замість 46 |
| `LIST_SEND_DELAY_SECONDS` | 0.3 | пауза **лише** між картками списку; кнопки відповідають миттєво |
| `STATUS_STEP_SECONDS` | 0.4 | щоб значки в рядку стану перемикались по одному, а не разом |
| `SLOW_AFTER_SECONDS` | 5 | середина таймауту; звичайний фетч ~1.2 с, тож спрацьовує лише коли справді гальмує |
| `DEFAULT_CACHE_TTL_SECONDS` | 120 | кеш етапу 1; протухле виселяється в `get`/`put`, інакше ріс би вічно |

## 5. Заміри (щоб не робити заново)

Зроблено в контейнері; на E2.1.Micro закладати в 1.5-3 рази повільніше.

- **Рендер картки:** 12.4 мс, PNG 20 КБ → ~80 карток/с в один потік.
- **Парсинг фіду** (60 вакансій): 16 мс.
- **Надсилання картки:** ~250 мс (з реального логу сервера).
- **БД:** ~234 Б на запис. 100 юзерів × (200 вилучених + 20 обраних) = 4.9 МБ.
- **Пам'ять:** ~338 КБ на юзера (hidden+favorites+vcache+seen) → 33 МБ на 100.
- **Клік «Не показувати»** при 200 вилучених: 2.8 мс (перезапис усіх рядків).
- **Прогін джоби** на 2 категоріях: фетч 8 джерел 1.24 с, разом 2.7 с.

**Відомі слабкі місця, які ще не полагоджені:** `vcache_{uid}` і `seen_{uid}`
ростуть без межі до рестарту; `_replace_table` переписує всі рядки користувача
на кожен клік; `max_vacancies_per_source = 100` дозволяє одному пошуку
згенерувати до 1000 карток.

## 6. Що в роботі

1. **Логи фідів за повний день.** 30.07 кількість «завантажено N за сьогодні»
   падала: 15 → 13 → 20 → 18 → 2 → 1 → 0. Між 11:00 і 13:00 UTC PID був той
   самий, тобто код не мінявся. Помилок завантаження за добу **не було жодної**.
   Причина не з'ясована. Дивитись у день без деплоїв:
   ```bash
   journalctl -u findmyjob-bot --since "24 hours ago" | grep "завантажено"
   journalctl -u findmyjob-bot --since "24 hours ago" | grep "feeds.fetcher"
   journalctl -u findmyjob-bot --since "24 hours ago" | grep "FILTER" | tail -40
   ```
   Формат рядка про помилку тепер містить номер спроби: `(спроба 1/3)`.

2. **Вакансії без дати — тиждень спостереження** (до ~06.08). Лічильник у
   `notifier._fetch_today`. Рахувати лише прогони, де «завантажено» не нуль:
   ```bash
   journalctl -u findmyjob-bot --since "24 hours ago" | grep "без дати" | grep -v "завантажено 0"
   ```
   Якщо трапиться ненульове — відсівати такі вакансії в `_fetch_today` (2 рядки),
   ручний пошук не чіпати. Якщо скрізь нулі — прибрати лічильник.

3. **Один запит на джерело замість запиту на категорію.** Зараз 4×N; мета — 4
   запити, у кожному всі обрані категорії. Перевірити емпірично: чи DOU приймає
   кілька `category`, і чи працює в Djinni `any_of_keywords` (АБО) замість
   `all_keywords` (І). **Складність:** зникає прив'язка вакансії до категорії, а
   від неї залежать розбивка у зведенні, `hidden_for_categories`, самозцілення
   `categories` у вилучених і фільтрація в джобі сповіщень.

4. ~~NDA-All знаходить 0 вакансій~~ — **виправлено.** Дві окремі причини,
   обидві підтверджені на реальному дампі сторінки (943 КБ, наданому
   користувачем):
   - Справжні посилання — `href="./vacancy/slug"` (відносний шлях), а не
     `href="/vacancy/slug"` (кореневий), який очікував старий селектор.
     Виправлено в `findmyjob/feeds/nda.py`: `_VACANCY_HREF_RE = r"^\.?/vacancy/"`
     приймає обидва варіанти, посилання будується через `urljoin(NDA_URL,
     href)` замість конкатенації рядків (пряма конкатенація дала б биту
     адресу `"https://nda.in.ua./vacancy/x"`).
   - Назва картки зліплювалась із сусідніми тегами-бейджами
     ("Бронювання", категорія) в одну кашу ("Marketing Project
     ManagerБронюванняMarketing"), бо `a.get_text()` бере весь текст
     картки без розбору. Виправлено: назва береться саме з `<h6>` усередині
     картки (підтверджено — рівно один `<h6>` у кожній із 226 знайдених
     карток на реальному дампі), з відкатом на весь текст картки, якщо
     розмітка колись зміниться й `<h6>` зникне.

   Супутньо виправлено: при виборі лише `NDA-All` рядок стану
   `Djinni I ⏳ : ... : DOU II ⏳` більше не показується (він застрягав
   назавжди — RSS-подій для DOU/Djinni там ніколи не було), і
   `format_vacancy()` тепер пропускає рядок "Дата публікації", коли
   `vacancy.published` порожній (раніше показувався завжди, навіть
   порожнім, — NDA-вакансії оголили цю прогалину в правилі "порожні поля
   пропускаються"). Картки для NDA-All ідуть тим самим шляхом, що й
   DOU/Djinni — жодного окремого рендеру.

   Ще три правки (той самий тиждень): `max_vacancies_per_source` (100) на
   NDA-All не діє (єдиний спільний список без розбивки на категорії, обрізати
   недоцільно); `BeautifulSoup` парсить `response.content` (байти), а не
   `response.text` — інакше `requests` вгадує кодування як latin-1 і кирилиця
   в назвах перетворюється на мохібейк (`ÐÐ½Ð¶ÐµÐ½ÐµÑ...`); картка NDA-вакансії
   більше не показує "🙈 Не показувати" (список спільний, ховати нема від
   чого) — лишається один рядок `⭐ В обране` / `🔗 Відкрити`.

   **Еталонний список і "Показати нові".** Нова таблиця `nda_baseline`
   (`storage.py`) — знімок NDA-All, з яким звіряють поточний стан. Пишеться
   **лише вручну**, кнопкою `🔄 Оновити еталон` (нижнє меню, лише коли обрана
   NDA-All, і лише для `Settings.admin_user_id` — з `ADMIN_USER_ID` у `.env`,
   `None` за замовчуванням = кнопка нікому не показується). Кнопки `📅/📆/📋`
   (періоди) замінюються на `🆕 Показати нові` (дифф поточного фетчу проти
   `nda_baseline` за посиланням, з підтвердженням Так/Ні) і `📋 Показати всі`
   (без порівняння) — обидві реалізовані в новій групі обробників
   `findmyjob/bot/handlers/nda.py` (`NdaActionHandlers`), реюзають
   `session.pending_vacancies` і `VacancySender.send_all()` так само, як
   звичайний пошук. Якщо еталон порожній (ще ніхто не натискав "Оновити") —
   "Показати нові" покаже геть усе як "нове", це очікувано.

   **Виправлено після першого реального використання:** `get_nda_source()` /
   `refresh_nda_source()` викликались напряму в async-обробнику (без
   `asyncio.to_thread`) — синхронний `requests.get()` блокував увесь event
   loop (усіх користувачів бота одночасно, не лише один чат) на час запиту.
   Найпомітніше на холодному кеші, тобто саме на перший вибір NDA-All.
   Обгорнуто в `asyncio.to_thread` + додано `⏳ Запрошую інформацію...` перед
   фетчем (`show_new`/`show_all`), як і в звичайному пошуку. Також додано
   кнопку `🔄 Переобрати категорії пошуку` (`build_reselect_keyboard()`) до
   всіх "глухих кутів" сценарію: "👍 Добре, почекаємо оновлень!" (Ні),
   порожній дифф ("нових немає") і порожній повний список.

   **NDA-All додано і в сповіщення** (не лише пошук). Ключова відмінність від
   пошуку: тут вона НЕ ексклюзивна — звичайна категорія в тій самій квоті в 5
   (`NOTIFY_FLOW.categories = DISPLAY_CATEGORIES`, значок 🔒 прибрано —
   `CategoryFlow.nda_locked_badge`, `False` для сповіщень). Причина: у
   пошуку NDA-All — самодостатній конвеєр, що замінює собою DOU/Djinni; у
   сповіщеннях вона просто ще одна незалежна лінія розсилки поряд з рештою
   обраних категорій, тож поєднувати можна.

   Дедуп для сповіщень NDA-All **інший**, ніж для решти категорій:
   персональний накопичувальний журнал (`notification_sent`) тут не підходить
   (немає дати публікації — "за сьогодні" не має сенсу). Замість цього —
   окрема таблиця `nda_notification_baseline` (один спільний знімок, БЕЗ
   `user_id`) і окремий шкедулер `findmyjob/bot/nda_notifier.py`
   (`NdaNotificationDispatcher`), тричі на день: **10:00, 14:00, 20:00**
   (`Europe/Kyiv`). Алгоритм (дослівно за запитом користувача): фетч
   поточного стану → дифф проти знімку → розсилка діффу підписаним на
   NDA-All → знімок ПОВНІСТЮ замінюється щойно зафетченим (не накопичується,
   на відміну від `notification_sent`).

   **Сплячий режим** (додано за окремим проханням): якщо жоден підписник не
   має NDA-All серед своїх категорій, прохід виходить одразу, ще ДО фетчу —
   ні запиту до `nda.in.ua`, ні оновлення знімку. Знімок лишається
   "замороженим" до першої підписки; після неї наступний прохід звірить
   його з поточним станом сайту як зазвичай (можливо, з великим діффом,
   якщо сайт устиг істотно змінитись за час сну — це очікувано).

   Головний
   погодинний шкедулер (`notifier.py`) тепер явно виключає `NDA_CATEGORY` зі
   своїх категорій — інакше підписник на NDA-All отримав би сповіщення
   двічі; якщо єдина категорія користувача — NDA-All, основний прохід
   узагалі пропускає RSS-фетч (порожній список категорій після фільтра
   інакше впав би на `AVAILABLE_CATEGORIES` через `categories or
   AVAILABLE_CATEGORIES` у `VacancyFeedService.fetch()` — довелось явно
   перевірити на порожнечу перед викликом).

5. **21 віддалена гілка `claude/*`** на GitHub — усі влиті, локальні прибрано.

6. **Тестів немає в репозиторії.** За сесію написано ~20 перевірочних скриптів
   (повтори фетчера, рядок стану, дедуплікація, парсер компанії, розсилка,
   паралельність, пейсинг, складання застосунку) — усі жили в scratchpad і
   зникли. Варто оформити їх як `tests/` з pytest: без цього кожна наступна
   сесія перевіряє те саме заново.
